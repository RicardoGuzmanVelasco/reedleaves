# Reglas del proyecto

- Hablar con el usuario en español técnico simplificado: frases cortas, decisiones claras, sin verborrea.
- Antes de cambiar arte, UX, animaciones o interfaz, leer `docs/frontend/DESIGN.md`.
- Respetar siempre los tres pilares: simplicidad funcional, pomposidad estética y pocos casos de uso.
- Copy de interfaz: incluir solo texto funcional, necesario o ya aprobado. No inventar slogans, frases promocionales ni texto decorativo de relleno. Ejemplo: «Entrar / Sign in» sí; «Tus libros, allá donde estés…» no.
- Mantener el carácter expresivo, amable y animado de las referencias Duolingo y Forest.
- La interfaz y las traducciones editoriales de libros tendrán español e inglés. El idioma original de libros y barajas es independiente. La plataforma sigue pendiente de decisión.
- Las exploraciones en `brand/` son propuestas; no convertirlas en decisiones aprobadas.
- El primer logo de tarjetas y estrella está descartado.
- Entorno Node: usar la versión de `.node-version`; al abrir un worktree nuevo, ejecutar `npm ci` si falta `node_modules` antes de iniciar la app o las pruebas.
- Verificación: antes de cerrar un hito o publicar cambios de código, ejecutar `npm test` completo con la versión de `.node-version` y exigir salida 0. El comando incluye el build. Las pruebas relacionadas sirven durante la iteración; no sustituyen la suite al cerrar. Un fallo previo no se considera aceptado: corregirlo o informar del bloqueo sin declarar la verificación completa.
- Pruebas con sockets: la suite abre servidores HTTP de prueba en puertos efímeros de `127.0.0.1`. Ejecutar `npm test` y cualquier otro comando de pruebas o desarrollo que llame a `server.listen` con `sandbox_permissions: "require_escalated"` desde el primer intento, justificando que necesita abrir listeners locales. No hacer antes un intento restringido. Si aun así aparece `listen EPERM`, repetir el mismo comando con permisos elevados; no dejar el EPERM como resultado final ni tratarlo como fallo de la aplicación.
- Pruebas: reutilizar `test-support/reader-state.mjs` para estados base de vistas. Comprobar contratos funcionales y accesibles en su contexto, sin fijar envoltorios, SVG o copy incidental. En migraciones, usar esquemas históricos inmutables de `server/fixtures/migrations/`; no construir versiones antiguas mediante reemplazos del SQL actual ni rebajar solo su número de versión.
- Tiempo y fechas: antes de calcular o mostrar horas, fechas, zonas horarias, ciclos, plazos o cuentas atrás, localizar y reutilizar la fuente centralizada del proyecto. Si la regla temporal es nueva y aún no está centralizada, añadirla allí primero y hacer que los consumidores la usen; no duplicar constantes ni algoritmos temporales en la interfaz, el servidor o las pruebas.
- Pruebas de IA: usar proveedores simulados. No hacer llamadas reales a OpenAI para comprobar el autorrelleno salvo petición expresa del usuario; consumen su saldo.
- Cuando haga falta contexto de avances recientes o estado operativo, leer `docs/development/README.md` y la entrada más reciente del diario. El código y la configuración del repo son la fuente de verdad técnica.
- Render: usar el workspace **RGV** (`tea-db59i2nlk1mc73978ao0`) para los servicios de este proyecto. La base de producción está en Supabase, no como instancia PostgreSQL de Render.
- Operaciones de catálogo: al mover, borrar o reordenar tarjetas, mantener posiciones consecutivas `1..N` en cada grupo de hermanas (`deck_id`, `parent_id`), incluidas las tarjetas raíz. Mover tarjetas exige reordenar tanto el origen como el destino en la misma transacción. Si los índices únicos impiden intercambiar posiciones directamente, usar posiciones temporales libres antes de asignar las definitivas. Conservar los IDs, el contenido, las fechas y las referencias de las notas; incluir sus descendientes y asegurar que tengan texto en el idioma de la baraja de destino.
- Verificación de datos en producción: antes de confirmar una operación de catálogo, validar sus invariantes, no solo el número de filas modificadas. Usar `readCatalog`/`checkCatalog` o comprobaciones SQL equivalentes de orden, jerarquía, referencias e idiomas. Tras confirmar, comprobar que `/api/catalog` devuelve HTTP 200 con un catálogo válido y verificar el resultado solicitado. `/api/health` no basta: puede responder correctamente aunque el catálogo esté roto. Si falla la validación, revertir la transacción; si el fallo aparece después, reparar o revertir el cambio antes de dar la operación por terminada.
- Git: trabajar en una rama del worktree y usar `main` como destino. No subir ramas ni abrir PR hasta que el usuario lo pida expresamente. Una petición de implementar o corregir no autoriza publicar. No hacer push directo a `main`.
- Git en worktrees: antes de cerrar un hito, comprobar `git rev-parse --git-dir`; el directorio Git puede estar fuera de la carpeta del proyecto y de las rutas escribibles del sandbox. Si `git add` o `git commit` falla con `Operation not permitted` al crear `.git/worktrees/.../index.lock` u otro archivo de metadatos, reintentar la misma operación autorizada con `sandbox_permissions: "require_escalated"` y justificar que solo escribe los metadatos Git de este worktree. No abandonar el commit ni dejar el fallo como nota sin intentar esa vía; no redirigir el índice ni alterar permisos como sustituto. Si la revisión automática rechaza la escalada, informar claramente que el hito queda sin commit y citar el bloqueo exacto.
- Integración: la CI ejecuta la suite completa y, si pasa, integra automáticamente con squash los PR listos del propio repositorio. No integrar a mano ni saltarse checks con `--admin`. Si hay conflictos, la rama queda desactualizada o falla CI, corregirlo antes de integrar. Los PR en borrador y los procedentes de forks no se integran automáticamente.
- Seguimiento de entrega: no seguir la CI, el merge, la CI de `main` ni Render por defecto, aunque la petición incluya push, PR o despliegue. Tras publicar, informar del PR o deploy iniciado y detenerse. Continuar el seguimiento hasta el resultado final solo si el usuario lo pide expresamente. Si la entrega implica un riesgo material o es especialmente importante, explicar el motivo y proponer ese seguimiento; esperar a que el usuario lo autorice antes de hacerlo. Con autorización, avisar si falla un check, la integración o el deploy, con enlace, causa y siguiente acción; corregir lo que esté dentro del alcance. No declarar éxito de una entrega como completada si el resultado aún no se ha verificado.
- Tras una integración confirmada durante un seguimiento autorizado, la CI elimina la rama remota; actualizar `main` local y borrar la rama temporal local. Acumular cambios relacionados y hacer commit al cerrar hitos grandes. Prima el pragmatismo; no exigir commits atómicos ni nombres estrictos. No versionar bases locales, copias, credenciales o secretos.
