# 2026-10-31 — Flujo SDLC con Staging

- El trabajo se concentra en la rama compartida `Staging`, creada desde `main`. Los agentes no crean ramas por tarea ni PRs.
- Cada push a `Staging` ejecuta lint, build, la prueba de recuperación PostgreSQL y la suite completa `npm test` con PostgreSQL real.
- Si todo pasa, el workflow comprueba que `Staging` contiene el `main` actual, publica el estado `Build and tests` para ese SHA y hace fast-forward de `main` al mismo SHA. Si `main` avanzó o diverge, la promoción falla sin sobrescribirlo; hay que actualizar `Staging` y volver a probar.
- Render está configurado para desplegar `main` cuando pasan los checks. El commit promovido es exactamente el que pasó CI en `Staging`.
- GitHub no ofrece una regla para impedir que alguien cree una PR dirigida a `main`. Se añade `Reject pull requests to main`, que falla con una instrucción para usar `Staging`. La conexión disponible puede leer reglasets pero no administrarlos; no había reglasets configurados.
- `workflow_dispatch` permite ejecutar la validación manualmente, pero no promueve commits. La promoción solo ocurre en pushes a `Staging`.
